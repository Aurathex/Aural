# Aural v0.2 · A — Adaptive STT + Hardware Test

Sub-project A of `2026-09-26-aural-v0.2-roadmap.md`. Status: **design approved in chat
2026-09-26; spec awaiting owner review.**

## Goal

Aural picks and recommends speech models from what **this PC** can actually do, measured
on this PC, across CPU, NVIDIA GPUs and AMD GPUs, at several accuracy/speed levels, with
streaming-capable models available for sub-project B. Nothing is hard-coded as the
universal best.

## Out of scope for A

Showing partial text while speaking (B), text post-processing (C), history (D), CUDA
runtime packs (the M0 benchmark showed CUDA no faster than Vulkan on the RTX 4070),
non-English UI.

## 1. Compatibility unit: catalog v2

A **variant** is one runnable combination: **Model + Runtime + Backend + Precision**.
Recommendations, labels, downloads and benchmarks all work per variant.

```text
Catalog v2
  models[]:
    id, name, family ("parakeet" | "whisper" | "moonshine" | …), description,
    languages[], license { id, url, attribution }, source
    variants[]:
      id                  e.g. "parakeet-tdt-0.6b-v3/onnx/directml/int8"
      runtime             "onnx" | "ggml"          (+ "llama" only if a spike says go)
      backend             "cpu" | "directml" | "vulkan"
      precision           "int8" | "fp16" | "fp32" | "q5_0" | "q8_0" | …
      streaming           bool   (the engine can produce partial results)
      files[]             { name, url (pinned commit), sha256, size }   shared files may repeat
      min_ram_mb, min_vram_mb
      reference           { wer, p50_ms, rtf, ram_mb, vram_mb } measured on the
                          reference PC (docs/benchmarks), used for estimates
```

- Files are stored per model, not per variant. Variants of one model that use the same
  files (for example Parakeet int8 on CPU and on DirectML) share one download.
- **Migration:** v1 model ids still resolve. `parakeet-tdt-0.6b-v2-int8` maps to
  `parakeet-tdt-0.6b-v2/onnx/cpu/int8`, and the Whisper ids map likewise. Installed
  files, receipts and the saved active model keep working without a re-download. Settings
  gain `stt.active_variant`, filled in from `stt.active_model` on first start.
- The catalog is still compiled into the app. It is not fetched at runtime.
- Validation, as in v1: pinned HTTPS URLs, SHA-256 on every file, unique ids, known
  runtime/backend/precision values. Invalid catalogs fail the build's tests, not the
  user's app.

## 2. Runtimes, backends and models

No new heavy runtimes in A. The two existing worker processes are extended, so v0.1's
crash isolation, restart and kill-switch behaviour stay.

| Worker | Backends | Candidate models |
|---|---|---|
| `aural-stt-onnx` (transcribe-rs 0.3.11 + ONNX Runtime 1.24.2) | CPU, **DirectML** (NVIDIA, AMD, Intel; `DirectML.dll` already ships) | Parakeet TDT 0.6B v2 (current) and **v3** (int8), **Moonshine** tiny/base and the streaming variant, plus others transcribe-rs supports (Canary 1B v2, SenseVoice) if they earn a place in the benchmark |
| `aural-stt-ggml` (whisper.cpp 1.8.3) | CPU, **Vulkan** (NVIDIA, AMD) | Whisper base.en / small.en / **large-v3-turbo**, **Distil-Whisper large-v3.5** |

- **Vulkan in the installer.** The ggml worker is built with Vulkan. The Vulkan loader
  comes with the GPU driver, so nothing extra is downloaded. Installer growth is measured
  and reported. If it grows by more than about 30 MB, the Vulkan backend moves to an
  optional download.
- **DirectML** uses the `ort-directml` execution provider. `ort` is already statically
  linked against a DirectML-capable ONNX Runtime.
- **Backend selection** stays explicit. A variant names its backend; a worker that
  cannot initialise it reports an error, and never silently falls back to the CPU (v0.1
  already enforces this for Whisper, and A adds it for ONNX).
- **Investigation spikes, go/no-go** (time-boxed, each written up in `docs/spikes/`):
  - **Nemotron Speech Streaming 0.6B** (NVIDIA, license "other"; GGUF and ONNX exports
    exist from third parties).
  - **Qwen3-ASR 0.6B** (Apache-2.0; GGUF and ONNX exports).

  Each is integrated only if all of these hold: (1) a runtime that builds and runs on
  Windows x64 on CPU and at least one GPU backend, (2) a license that allows use by Aural,
  with the terms recorded, (3) benchmark results that beat an existing variant on
  accuracy, speed or streaming. If Qwen3-ASR needs llama.cpp, that runtime would be shared
  with sub-project C's local LLM, which is recorded as an argument for it, not a reason on
  its own.
- Every model added passes the same checks: pinned files, verified hashes, a license
  suitable for Aural, attribution in the notices and About page, and real-model
  integration tests.

## 3. Hardware Test

Runs automatically on first start (after v0.2 is installed or updated) and on demand
from Settings → Models → **Run hardware test**. The user can cancel it at any point, and
dictation keeps working with the current model while it runs.

### 3.1 Detect

- CPU: name, physical/logical cores, AVX2/AVX-512.
- RAM: total and free (`GlobalMemoryStatusEx`).
- GPUs: DXGI adapter enumeration (vendor, name, dedicated video memory, software-adapter
  flag), including hybrid laptops with more than one GPU.
- **Backends are proven, not assumed.** Each backend is marked available only after a
  worker has actually initialised it on a real device: Vulkan through whisper.cpp's
  device list, DirectML through an ONNX Runtime session. Failures are recorded with their
  reason.

### 3.2 Calibrate

- With the user's consent (one prompt, showing sizes), two small **probe models** are
  downloaded, one per runtime: Whisper tiny.en (ggml) and Moonshine tiny (ONNX), about
  80 MB in total. They are verified like any other model.
- Each probe is benchmarked on every available backend using the **built-in test
  clips**: about 20 LibriSpeech test-clean utterances (CC BY 4.0, credited), fixed
  across versions, stored compressed in the installer (1–2 MB), with reference
  transcripts.
- If the user declines the probe download, detection results are still shown. Labels
  wait until a model is downloaded and measured.

### 3.3 Estimate

Every variant that is not downloaded gets **estimated** metrics:

`estimated latency = probe latency on this PC × (reference latency of the variant ÷
reference latency of the probe)`

This uses the same runtime and backend, with reference numbers from the catalog. WER is
taken from the reference benchmark (accuracy doesn't depend on hardware). RAM and VRAM
come from the reference plus a margin. Estimates are shown with an "estimated" mark.

### 3.4 Measure

When a variant is downloaded, it is benchmarked automatically on the built-in clips
(usually under a minute; it can also be re-run by hand). Its numbers and labels are then
marked **measured**.

### 3.5 Metrics per variant

- WER on the built-in clips (the pooled word error rate the bench already uses).
- p50 and p95 transcription latency.
- Real-time factor.
- Model load time.
- Peak RAM (worker working set) and VRAM (DXGI budget query for the worker process;
  "not measured" where unavailable).
- **Stability:** the clips are run 3 times. Recorded: crashes, timeouts, backend
  fallbacks, and latency spread (p95/p50). A crash, timeout or fallback makes the variant
  Not Suitable, with the reason.

Results are stored in `%LOCALAPPDATA%\com.aurathex.aural\hardware.json`, keyed by variant
id and a hardware fingerprint (CPU, GPUs, driver versions, RAM). A changed fingerprint
(new GPU, new driver) marks results stale and offers a re-run.

## 4. Labels

Computed by one pure function from the metrics (measured or estimated) and the hardware
facts. Five labels:

| Label | Rule |
|---|---|
| **Recommended** | At most one per PC. Among suitable variants: WER within the margin of error of the best WER (95% margin computed from the clip set's word count, 1.96·√(p(1−p)/N); about ±1.5 pt for ~400 words); p50 at or under the dictation budget (500 ms); fits in RAM/VRAM with headroom (at most 50% of free RAM, 70% of VRAM); stable. Ties go to lower latency, then smaller footprint. |
| **Most Accurate** | Lowest WER among suitable variants; ties within the margin go to the faster one. |
| **Fastest** | Lowest p50 among suitable variants whose WER is at most 1.5× the best. |
| **Streaming** | `streaming: true` and RTF ≤ 0.3, so partial text keeps up while speaking. |
| **Not Suitable** | Required runtime/backend unavailable, won't fit in RAM/VRAM, RTF > 1, or unstable. The UI shows the reason, e.g. "Needs about 6 GB of video memory" or "No compatible GPU". |

- A usable variant with none of these simply has no label.
- One variant can hold several labels (e.g. Recommended + Most Accurate).
- **Active model after the test:** the current choice is kept unless it is now Not
  Suitable, in which case Aural switches to Recommended and tells the user. A fresh
  install offers Recommended as the model to download.

## 5. UI

- **First run:** Welcome → Hardware test (what will be checked, the probe download
  prompt, progress) → Models page with labels → download the Recommended variant.
- **Models page:**
  - One row per model, with its variants as choices (e.g. "CPU · int8", "GPU (DirectML)
    · int8").
  - Labels as small black/white chips.
  - WER, speed (p50 and RTF), load time, RAM and VRAM, each marked measured or estimated.
  - Download / Use / Remove, as today.
  - Hardware summary at the top (CPU, GPUs with backends, RAM) and "Run hardware test".
- Keeps the v0.1 visual language (minimal, black/white/neutral) and accessibility
  (keyboard navigation, screen-reader labels).

## 6. Error handling

| Situation | Result |
|---|---|
| Backend init fails at runtime | Error reported, variant marked Not Suitable ("GPU backend failed to start"), no silent CPU fallback. The active model falls back to the Recommended CPU variant, with a notice. |
| Probe download fails or is declined | Detection still shown, labels wait. |
| Benchmark worker crashes or times out | Counted in stability, worker restarted, next variant continues. |
| Hardware changed | Results marked stale, re-run offered, labels shown as estimated until then. |
| Catalog v1 data from v0.1 | Migrated in place; nothing re-downloaded. |

## 7. Testing

- **Pure unit tests:**
  - Catalog v2 parsing and validation, and v1 → v2 id migration.
  - Label rules against fixture profiles: a CPU-only 8 GB laptop, a CPU + RTX 4070 laptop,
    a desktop with an AMD GPU and a 4-core low-RAM PC. Each checks Recommended, ties and
    margins, Not Suitable reasons, and that one variant can hold several labels.
  - Estimation arithmetic, and hardware-fingerprint staleness.
  - DXGI parsing through an injectable adapter list.
- **Worker tests:** ONNX DirectML and ggml Vulkan backend selection. A requested GPU
  backend that cannot start is an error, never a CPU result (fake worker plus real-hardware
  ignored tests).
- **Real-model integration tests** (ignored by default, run on the reference PC) for each
  new engine and backend: Parakeet v3, Moonshine (plus streaming), Distil-Whisper,
  turbo on Vulkan, and Parakeet on DirectML.
- **Hardware test end to end** on the reference PC: detection, probe calibration,
  measure-on-download, labels, stored results.
- **Benchmarks:** the full matrix on the RTX 4070 Laptop GPU and the CPU (LibriSpeech-100,
  as in M0) for every integrated variant, in `docs/benchmarks/`. Estimates are checked
  against measurements: the estimated p50 must be within ±35% of the measured p50 for
  each variant (reported per variant).
- The full v0.1 validation suite stays green.

## 8. Risks

| Risk | Mitigation |
|---|---|
| DirectML slower than the CPU for some models | Benchmarks decide; labels reflect it; nothing is assumed. |
| Vulkan grows the installer | Measured; optional download if more than about 30 MB. |
| AMD GPU paths are unverifiable here | Designed and build-tested; labelled "estimated" until measured; hardware reports from users planned for later. |
| Third-party model exports change or disappear | Pinned commit URLs and hashes, as in v1. |
| Estimates mislead | Clearly marked, replaced by measurements on download; accuracy of the estimates is reported. |
